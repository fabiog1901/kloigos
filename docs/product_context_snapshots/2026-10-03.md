# Kloigos Product Context Snapshot

**Generated:** 2026-10-03  
**Audience:** Codex, maintainers, documentation authors, product and architecture contributors  
**Purpose:** Canonical product-level context for interpreting, implementing, and documenting Kloigos.

> **Important:** This snapshot describes the intended/current Kloigos product as a coherent whole. Features described here should be treated as product capabilities and architectural direction even when individual implementation work remains incomplete.
>
> Detailed architectural behavior belongs in `docs/design/`. This snapshot establishes the product model and relationships between the major concepts.

---

## 1. Executive Definition

Kloigos is a **Linux-native bare-metal compute platform** that turns a heterogeneous fleet of physical Linux servers into a programmable internal compute cloud.

It provides cloud-like infrastructure primitives while using standard Linux mechanisms rather than virtual machines or containers as its fundamental infrastructure abstraction.

Kloigos allows users to request isolated compute capacity while administrators retain control over:

- physical hardware;
- CPU delivery policy;
- placement;
- networking;
- storage;
- tenancy;
- security;
- pricing;
- lifecycle;
- resource enforcement.

A concise definition is:

> **Kloigos turns a heterogeneous bare-metal Linux fleet into a programmable internal compute cloud using standard Linux primitives.**

---

## 2. Product Philosophy

Kloigos is based on a simple principle:

> Modern Linux already contains many of the primitives required to partition and manage powerful physical servers.

Instead of introducing a hypervisor, guest operating systems, or mandatory containerization, Kloigos composes existing Linux capabilities into a controlled infrastructure platform.

Core technologies include:

- systemd;
- cgroups v2;
- Linux users and groups;
- filesystem ownership and permissions;
- LVM;
- standard Linux networking;
- nftables;
- AppArmor where supported;
- OpenSSH;
- Ansible for deterministic host operations.

The architectural preference is:

> **Use standard Linux primitives where they provide the required capability instead of creating unnecessary proprietary abstractions.**

The control plane owns desired state.

Physical Linux Hosts enforce that state.

---

## 3. What Kloigos Is Not

Kloigos is not:

- a hypervisor;
- a virtual-machine platform;
- a system-container platform;
- a container orchestrator;
- a Kubernetes replacement;
- a Kubernetes distribution;
- an overlay-network platform;
- a mandatory application packaging system;
- a general-purpose secret manager;
- a payment processor.

Applications running on Kloigos do not need to be containerized.

Compute Units do not contain their own operating system or kernel.

Compute Units on the same physical Host share the Host Linux kernel.

Kloigos therefore does not claim VM-grade kernel isolation between mutually hostile workloads.

Where stronger kernel-level isolation is required, Kloigos can use **Dedicated Tenancy** to prevent different organizations from sharing the same physical Host.

## 5. Physical Hosts

A **Host** is a physical Linux server managed by Kloigos.

Kloigos discovers factual hardware characteristics including, where relevant:

- CPU architecture;
- CPU vendor and model;
- sockets;
- cores;
- threads;
- NUMA topology;
- memory;
- GPUs/accelerators;
- storage characteristics.

The Host represents physical infrastructure.

Higher-level Kloigos abstractions determine how that infrastructure is classified, exposed, and allocated.

---

## 6. Host Families

A **Host Family** is an administrator-defined classification of physical Hosts with similar hardware characteristics.

Examples might include:

```text
amd-epyc-gen4
intel-xeon-gen5
intel-xeon-legacy
gpu-h100
storage-dense-gen2
```

The fundamental distinction is:

> **Kloigos discovers what a machine is; administrators decide what that hardware means in their environment.**

Kloigos does not maintain a universal commercial taxonomy of CPU models or server types.

Host Families are infrastructure-facing and participate in placement eligibility.

They are distinct from general-purpose Host tags such as:

```text
datacenter=nyc1
rack=r12
environment=production
```

Host Families describe hardware classification.

They do not define CPU sharing or overcommit behavior.

---

## 7. CPU Policies

A **CPU Policy** describes how CPU capacity is delivered.

Examples include:

```text
dedicated
shared-standard
shared-economy
```

Conceptually:

```text
dedicated
    -> exclusive physical CPU ownership

shared-standard
    -> shared scheduling
    -> administrator-defined overcommit

shared-economy
    -> shared scheduling
    -> higher administrator-defined overcommit
```

CPU Policies describe semantics rather than a particular Linux implementation.

The exact implementation may use mechanisms such as:

```text
AllowedCPUs=
CPUWeight=
CPUQuota=

cpuset.cpus
cpu.weight
cpu.max
```

The appropriate mapping must be validated experimentally.

The architectural model must not depend on one particular cgroup or systemd implementation choice.

---

## 8. Logical CPU Managers

A **Logical CPU Manager** is a Host-local resource manager that owns a set of physical CPUs, implements one CPU Policy, and provides CPU capacity to Allocations.

It occupies a role analogous to LVM for storage:

```text
Storage                         CPU

Physical disks                  Physical CPUs
      |                               |
      v                               v
Logical Volume Manager          Logical CPU Manager
      |                               |
      v                               v
Logical Volume                  CPU assignment
```

Allocations do not consume CPU directly from a Host.

They obtain CPU capacity from a Logical CPU Manager.

---

## 9. Multiple Logical CPU Managers per Host

A Host may contain multiple Logical CPU Managers.

Example:

```text
Host: server-42
Physical CPUs: 0-63

Logical CPU Manager A
    CPUs: 0-31
    Policy: dedicated

Logical CPU Manager B
    CPUs: 32-63
    Policy: shared-standard
```

Another Host could contain:

```text
Logical CPU Manager A
    CPUs: 0-15
    Policy: dedicated

Logical CPU Manager B
    CPUs: 16-47
    Policy: shared-standard

Logical CPU Manager C
    CPUs: 48-63
    Policy: shared-economy
```

Physical CPU sets owned by Logical CPU Managers must not overlap.

Some CPUs may remain outside all Logical CPU Managers for Host operating-system or platform use.

Multiple Logical CPU Managers may also implement the same CPU Policy if administrators want separate resource domains.

---

## 10. Dedicated CPU

A Dedicated Logical CPU Manager assigns specific physical CPUs to Allocations.

Example:

```text
Manager CPUs:
0-15

Allocation A:
0-3

Allocation B:
4-11

Available:
12-15
```

The invariant is:

> **A physical CPU assigned to an active Dedicated Allocation cannot simultaneously be assigned to another Allocation.**

The Allocation records the specific physical CPUs assigned to it.

Future placement algorithms may consider:

- NUMA;
- sockets;
- SMT siblings;
- cache topology.

These refinements do not change the core Dedicated CPU model.

---

## 11. Shared and Burstable CPU

Shared CPU allows multiple Allocations to consume logical CPU capacity backed by the same physical CPU set.

For example:

```text
Physical CPUs:
16

Overcommit:
2:1

Logical CPU capacity:
32
```

An Allocation consumes logical CPU entitlement rather than owning specific physical CPUs.

Example:

```text
Allocation A:
8 logical CPUs

Allocation B:
4 logical CPUs

Allocation C:
8 logical CPUs

Allocated:
20

Available:
12
```

Admission is based on logical capacity, not current CPU utilization.

An idle Allocation still consumes its assigned logical capacity until that capacity is released.

---

## 12. CPU Entitlement and Bursting

Logical CPU quantity represents proportional CPU entitlement under contention.

For example:

```text
Allocation A:
4 logical CPUs

Allocation B:
8 logical CPUs
```

Under sustained contention, the expected relative CPU service is approximately:

```text
A : B = 1 : 2
```

Shared CPU should be **work-conserving**.

If Allocation B is idle, Allocation A may consume otherwise unused physical CPU capacity.

This behavior is called **bursting**.

Bursting does not create additional schedulable logical capacity.

It simply allows idle physical CPU cycles to be used.

Kloigos does not initially require an AWS-style CPU credit system.

> **Burstable CPU means the ability to consume otherwise idle physical CPU capacity within the shared CPU domain.**

---

## 13. Shared 1:1 vs Dedicated CPU

A Shared CPU Policy may use a 1:1 logical-to-physical capacity ratio.

That does not make it equivalent to Dedicated CPU.

```text
Shared 1:1
    -> scheduler-shared CPU domain
    -> work-conserving
    -> no exclusive CPU ownership

Dedicated
    -> specific physical CPUs
    -> exclusive ownership
```

Therefore:

> **Shared 1:1 is not Dedicated CPU.**

---

## 14. Instance Classes

An **Instance Class** is an administrator-defined, user-facing compute product.

It packages infrastructure choices so users do not need to understand physical server models or CPU overcommit policies.

Example:

```yaml
instance_class:
  name: general-purpose

  eligible_host_families:
    - amd-epyc-gen4
    - intel-xeon-gen5

  cpu_policy:
    shared-standard
```

A user may request:

```yaml
instance_class: general-purpose

resources:
  cpu: 8
  memory: 32GiB
```

The user normally does not select:

- CPU vendor;
- physical Host;
- Logical CPU Manager;
- overcommit ratio;
- physical CPU IDs;
- CPU scheduler settings.

Those are infrastructure concerns managed by Kloigos.

---

## 15. Instance Class vs Resource Size

Instance Class and resource quantity are separate concepts.

For example:

```text
Instance Class:
general-purpose

CPU:
8

Memory:
32 GiB
```

Administrators may allow flexible sizing or define standardized allowed sizes.

Dynamic Compute Unit provisioning means these sizes do not require pre-created Compute Unit shapes.

Kloigos should not automatically expose the Cartesian product of every:

```text
Host Family
×
CPU Policy
×
resource size
```

Administrators deliberately define the products they want users to consume.

---

## 16. Dynamic Compute Unit Allocation

The **Dynamic Compute Unit Allocator** determines where resources required by an Allocation come from.

It answers:

> **Where can this request be placed, and which resources should it receive?**

For CPU placement, the Allocator searches Logical CPU Managers rather than raw Host CPU capacity.

Conceptually:

```text
User Request
      |
      v
Instance Class
      |
      +-- Eligible Host Families
      +-- CPU Policy
      |
      v
Compatible Logical CPU Managers
      |
      v
Associated Hosts
      |
      +-- memory
      +-- storage
      +-- IP availability
      +-- tenancy
      +-- Host state
      +-- other constraints
      |
      v
Placement
```

Selecting a Logical CPU Manager also identifies the physical Host.

---

## 17. Allocator Resource Model

The Allocator evaluates each resource according to its own resource model.

CPU requires the Logical CPU Manager abstraction because physical CPUs may be partitioned into multiple policy domains on the same Host.

Other resources do not need to be forced into an identical abstraction.

For example:

```text
CPU
    -> Logical CPU Manager

Memory
    -> Host capacity

Storage
    -> storage/LVM model

IP
    -> IP pool

Tenancy
    -> Host placement constraint
```

Kloigos should avoid introducing a generic Resource Pool abstraction merely for architectural symmetry.

New resource abstractions should be introduced only when the underlying resource semantics require them.

---

## 18. Authoritative Placement State

The Allocator operates against authoritative control-plane database state.

Relevant state includes:

- Hosts;
- Host Families;
- CPU Policies;
- Logical CPU Managers;
- Instance Classes;
- Allocations;
- memory capacity;
- storage state;
- IP pools;
- tenancy state;
- Host lifecycle state.

The Allocator should not interrogate every Host during placement to discover current capacity.

Available capacity should normally be derived from authoritative capacity and Allocation state.

For example:

```text
Logical CPU capacity
-
active logical CPU Allocations
=
available logical CPU capacity
```

Kloigos should avoid independently authoritative availability counters that can drift from Allocation state.

---

## 19. Placement Transactions

Placement and resource assignment use the control-plane database transaction model.

Serializable transactions protect concurrent placement decisions.

A successful placement transaction creates a complete and internally consistent resource assignment.

A failed transaction must not leave a partial Allocation.

Kloigos does not require a separate generic distributed reservation system unless future implementation constraints demonstrate a need for one.

---

## 20. Allocations

An **Allocation** is the durable workload identity and authoritative resource assignment.

An Allocation includes or references concepts such as:

- Allocation ID;
- owning organization;
- Unix identity;
- Instance Class;
- selected Host;
- selected Logical CPU Manager;
- CPU quantity;
- physical CPU assignment where Dedicated;
- memory;
- storage identity;
- IP address;
- SSH keys;
- security groups;
- tenancy;
- metadata/tags;
- metering history.

The current architectural rule is:

> **Allocation = durable workload identity and authoritative resource assignment.**

The Allocation persists independently from the particular Linux Compute Unit materializing it.

---

## 21. Dynamic Compute Unit Provisioning

The **Dynamic Compute Unit Provisioner** materializes an Allocation as a concrete Linux Compute Unit.

It answers:

> **How do these already-assigned resources become a Linux execution environment on the selected Host?**

Conceptually:

```text
Allocation
    |
    v
Dynamic CU Provisioner
    |
    +-- Unix identity
    +-- systemd
    +-- cgroups
    +-- CPU controls
    +-- memory controls
    +-- filesystem
    +-- LVM/storage
    +-- networking
    +-- nftables
    +-- SSH
    |
    v
Compute Unit
```

The Provisioner does not perform placement.

It consumes the placement recorded by the Allocator.

---

## 22. Allocator / Provisioner Boundary

The responsibility boundary is explicit.

```text
ALLOCATOR
--------------------------------
WHERE resources come from

Host
Logical CPU Manager
CPU assignment / entitlement
memory
storage
IP
tenancy
other placement decisions


PROVISIONER
--------------------------------
HOW assigned resources become
a Linux Compute Unit

systemd
cgroups
CPU enforcement
memory enforcement
filesystem
LVM
network configuration
nftables
Unix identity
SSH
```

The Provisioner must not silently choose another Host or Logical CPU Manager.

If placement must change, control returns to the Allocator.

---

## 23. Compute Units

A **Compute Unit (CU)** is the concrete Linux realization of an Allocation on a Host.

A CU may contain or enforce:

- CPU boundaries;
- CPU scheduling policy;
- memory limits;
- task/PID limits;
- storage;
- filesystem ownership;
- networking;
- security controls;
- SSH access.

A Compute Unit is not a VM.

It has:

- no guest operating system;
- no independent kernel;
- no virtual hardware requirement.

The current architectural distinction is:

> **Allocation = durable workload identity and authoritative resource assignment.**

> **Compute Unit = concrete Linux realization of that Allocation on a Host.**

This allows an Allocation to survive Compute Unit replacement or future movement between Hosts.

---

## 24. Networking Model

Every Allocation receives its own IP address.

Kloigos does not require an overlay network to provide workload addresses.

Addresses come from administrator-configured IP pools and are configured using standard Linux networking on physical Hosts.

Conceptually:

```text
Physical Host NIC
    |
    +-- Host IP
    +-- Allocation A IP
    +-- Allocation B IP
    +-- Allocation C IP
```

Kloigos uses nftables and standard Linux networking primitives to associate and enforce each address with the intended Compute Unit.

IP availability participates in placement.

A Host that has CPU and memory capacity but cannot satisfy the required network/IP constraints is not a valid placement.

The IP primarily belongs to the Allocation identity rather than merely to a temporary Compute Unit.

---

## 25. Network Security Groups

Kloigos provides control-plane-managed Network Security Groups for Allocations.

Security Groups describe permitted network traffic using concepts such as:

- protocol;
- port;
- source/destination CIDR;
- references to other Security Groups.

The model is:

> **Control-plane policy, Host-enforced.**

Kloigos compiles these policies into Host-level nftables enforcement.

Security Group identity follows the Allocation.

---

## 26. Storage and Persistence

Kloigos uses Linux-native storage mechanisms, including LVM, to provide controlled storage to Allocations.

Persistent storage belongs to the durable Allocation lifecycle rather than automatically to the temporary Compute Unit lifecycle.

Therefore:

> **Destroying or replacing a Compute Unit must not unintentionally destroy persistent Allocation storage.**

The Allocator determines whether required storage capacity can be satisfied.

The Dynamic CU Provisioner materializes the assigned storage on the selected Host.

---

## 27. SSH Access

SSH access is a core Kloigos capability.

Users may associate SSH public keys with Allocations.

Kloigos installs authorized public keys into the Allocation's Linux identity.

For generated key pairs:

```text
Generate key pair
      |
      +-- store public key
      |
      +-- return private key once
      |
      +-- do not retain recoverable private key
```

SSH access follows Allocation identity rather than physical placement.

---

## 28. Tenancy

Kloigos supports Shared and Dedicated Tenancy.

### Shared Tenancy

Allocations belonging to multiple organizations may coexist on the same physical Host.

### Dedicated Tenancy

A physical Host is restricted to one organization.

No Allocation belonging to another organization may share that Host while the dedicated tenancy relationship is active.

Tenancy is primarily a placement constraint enforced by the Allocator.

It is conceptually independent from Instance Class.

---

## 29. Metering, Pricing, and Chargeback

Kloigos supports allocation-based metering and administrator-defined pricing.

Pricing may depend on:

- Instance Class;
- CPU quantity;
- memory;
- storage;
- GPUs;
- tenancy;
- allocation duration.

Metering is based primarily on resources held by an Allocation rather than measured CPU utilization.

For example:

```text
8 logical CPUs allocated for 10 hours
```

is billable according to the applicable administrator-defined pricing even if the workload was idle for part of that period.

Pricing may change over time, and historical chargeback records must remain auditable.

Kloigos provides metering and chargeback/showback records.

It does not process payments.

---

## 30. K3s / Kubernetes on Kloigos

Kubernetes may run inside Kloigos Compute Units.

The initial target is K3s because of its lightweight operational model.

Conceptually:

```text
Physical Kloigos Host
    |
    +-- CU
    |    +-- K3s control plane
    |
    +-- CU
    |    +-- K3s worker
    |
    +-- CU
    |    +-- K3s worker
    |
    +-- CU
         +-- native Linux workload
```

Kloigos remains authoritative over the outer resource boundary.

K3s may subdivide resources delegated to its Compute Unit but must not escape that boundary.

Nested cgroup behavior and delegation are important validation targets, particularly for Shared CPU.

---

## 31. Validation Philosophy

Kloigos relies heavily on standard Linux enforcement mechanisms.

Configuration alone is not sufficient evidence that those mechanisms behave as intended.

The validation principle is:

> **Verify configured state, then exercise or deliberately attempt to violate the boundary and verify that Linux actually enforces it.**

The Validation Harness uses Ansible for deterministic orchestration and established Linux workload tools where appropriate.

Important validation areas include:

- Dedicated CPU exclusivity;
- Shared CPU proportional contention;
- Shared CPU bursting;
- CPU domain isolation;
- memory limits;
- storage limits;
- I/O behavior;
- process limits;
- networking;
- nftables;
- AppArmor;
- tenancy;
- dynamic provisioning;
- provisioning cleanup;
- nested cgroups/K3s.

Validation is initially intended to run manually from a development environment, for example:

```text
make validate
```

It should not depend on GitHub Actions for its initial operation.

## 32. Administrative Complexity vs User Simplicity

A core Kloigos design principle is:

> **Administrators own infrastructure complexity; users consume simple abstractions.**

Administrators configure concepts such as:

```text
Host Families
CPU Policies
Logical CPU Managers
Instance Classes
IP Pools
Tenancy policies
Pricing
```

Users consume concepts such as:

```text
Instance Class
CPU quantity
Memory quantity
Storage quantity
Tenancy
SSH keys
Security Groups
```

The platform translates between these layers.

Users should not need to understand:

- physical CPU numbering;
- CPU overcommit ratios;
- CPU scheduler weights;
- Host hardware models;
- Logical CPU Manager topology;
- nftables rules;
- LVM implementation details.

---

## 33. Resource Abstraction Principle

Kloigos should introduce abstractions when the underlying resource semantics require them.

It should not force all resources into a common abstraction merely for architectural symmetry.

For example:

```text
CPU
    -> Logical CPU Manager

Storage
    -> LVM/storage model

IP addresses
    -> IP pools

Memory
    -> Host capacity
```

A generic Resource Pool abstraction is not currently required.

This reflects a broader architectural preference:

> **Prefer the smallest abstraction that accurately models the resource.**

## 34. Architectural Invariants

The following invariants should guide future implementation and design work.

### Product

> Kloigos is Linux-native and bare-metal.

> Compute Units share the Host kernel.

> Kloigos does not require virtualization or containers.

### Hardware

> Kloigos discovers hardware facts.

> Administrators classify Hosts into Host Families.

> Host Families and CPU Policies represent different concerns.

### CPU

> Allocations obtain CPU capacity through Logical CPU Managers.

> A Host may contain multiple Logical CPU Managers.

> Logical CPU Manager physical CPU sets must not overlap.

> Dedicated CPU means exclusive physical CPU ownership.

> Shared CPU means logical entitlement within a shared physical CPU domain.

> Shared CPU should be work-conserving.

> Shared 1:1 is not equivalent to Dedicated CPU.

> Bursting does not create additional schedulable logical capacity.

### Instance Classes

> Instance Classes are administrator-defined user-facing products.

> Instance Classes select eligible Host Families and a CPU Policy.

> Users normally do not select raw overcommit ratios.

> Instance Classes do not represent pre-created Compute Unit inventory.

### Placement

> The Allocator decides where resources come from.

> CPU placement targets Logical CPU Managers.

> Selecting a Logical CPU Manager identifies the Host.

> Placement uses authoritative control-plane state.

> Serializable database transactions protect concurrent placement decisions.

### Allocation

> The Allocation is the durable workload identity.

> The Allocation is also the authoritative record of assigned resources and placement.

> A completed Allocation contains enough information for provisioning without another placement decision.

### Provisioning

> The Dynamic CU Provisioner materializes the Allocation.

> The Provisioner does not perform placement.

> Re-placement returns through the Allocator.

### Compute Units

> Compute Units are dynamically materialized Linux resource boundaries.

> Compute Units do not need to exist before an Allocation is requested.

> Compute Unit lifecycle is distinct from durable Allocation lifecycle.

### Networking and Storage

> IP addresses come from administrator-provided IP pools.

> Kloigos networking is Host-native rather than overlay-based.

> Persistent storage follows Allocation lifecycle rather than temporary CU lifecycle.

### Architecture

> Do not introduce generic abstractions merely for symmetry.

> Prefer deterministic, relational control-plane state.

> Prefer standard Linux mechanisms over proprietary infrastructure primitives where practical.

## 37. Guidance for Future Work

When implementing new Kloigos features:

1. Preserve the distinction between Host, Host Family, Logical CPU Manager, Instance Class, Allocation, and Compute Unit.
2. Keep placement logic in the Allocator.
3. Keep Host materialization logic in the Dynamic CU Provisioner.
4. Keep durable workload identity and resource assignment with the Allocation.
5. Avoid exposing infrastructure implementation details to users unless there is a clear product reason.
6. Avoid generic resource abstractions until multiple concrete resources demonstrate the same semantics.
7. Use authoritative relational control-plane state for placement and accounting.
8. Use Linux-native enforcement mechanisms wherever practical.
9. Validate enforcement experimentally rather than assuming configuration implies behavior.
10. Keep architecture deterministic enough that implementation tasks can be expressed as small, constrained GitHub issues.

## 38. Product Direction

Kloigos is evolving toward a model where administrators can add heterogeneous physical Linux servers to a fleet, classify and partition their resources, expose deliberate compute products, and allow users to request infrastructure without knowing the physical topology underneath.

The resulting experience should resemble an internal compute cloud:

```text
User requests:

general-purpose
8 CPU
32 GiB RAM
100 GiB storage
```

while Kloigos handles:

```text
Instance Class resolution
        |
Host Family eligibility
        |
CPU Policy
        |
Logical CPU Manager selection
        |
Host placement
        |
memory/storage/IP/tenancy validation
        |
Allocation
        |
Linux materialization
        |
Compute Unit
```

The objective is not to hide Linux.

It is to make a heterogeneous Linux bare-metal fleet **programmable, allocatable, enforceable, and operationally coherent** without requiring virtualization or container orchestration as the fundamental infrastructure layer.
